 A1. Database Design Principles
 1. One authoritative database serves web, mobile and reporting; no duplicate business database.

 2. Every business entity has an immutable internal primary key. Human-readable codes are separate display identifiers.

 3. Foreign keys enforce ownership relationships; important relationships are not stored only as free text.

 4. Transactional history is not hard-deleted through normal application workflows.

 5. Stock balances, customer outstanding, vendor payable and P&L; are derived from authoritative transactions or controlled
 materialized summaries, not manually maintained totals.

 6. Every event-related operational/financial row links to Event ID and Meal Session when applicable; general costs use an
 approved Overhead/Cost Centre.

 7. Standard, estimated and actual costing data are stored separately.

 8. Commercial and operational snapshots preserve historical values after master data changes.

 9. Concurrency-sensitive reservations/confirmations use database transactions and uniqueness/locking controls.

 10. Audit and approval history are append-oriented and cannot be silently replaced.

  Convention                       Frozen Rule

  Primary key                      UUID/opaque internal ID recommended; never business name as key.

  Display code                     Human-readable unique code, e.g. CUS-000001, EVT-000001; format configurable.

  Foreign key                      _id pattern in logical model.

  Money                            Fixed decimal numeric type; never binary floating point.

  Quantity                         Decimal numeric with UOM.

  Date/time                        Store timestamp with timezone handling; event local timezone preserved.

  Status                           Controlled enumerated/reference value; not arbitrary free text.

  Versioning                       version_no + effective timestamp + previous/reference where history is required.

  Audit stamps                     created_at/by, updated_at/by; sensitive changes additionally in audit log.

 A21. Database Constraints - FROZEN
   - Unique normalized customer phone/email constraints are warning/controlled uniqueness where shared family/business
     contacts make strict uniqueness unsafe.

   - Unique display codes per configured scope.
   - No stock movement with zero quantity unless explicit correction type allows it.
   - No negative money totals on normal invoices/bills except dedicated credit/reversal documents.
   - No cross-company finance posting without explicit inter-company design; not assumed in this freeze.
   - Closed event records reject unauthorized edits at backend and database/service validation layers.
   - Approval source record cannot change critical values while approval is pending without invalidating/restarting approval.
   - Inventory reservations cannot exceed permitted available/override logic without recorded exception.
   - Foreign-key delete actions default to RESTRICT for live transactional relationships.
   - Every financial/stock multi-row write runs in one transaction to prevent partial posting.
 OWNER CONFIGURATION REQUIRED - NOT INVENTED

   - Exact database engine and hosting choice.
   - Display code formats/sequences.
   - Data-retention years for non-statutory records.
   - Multi-company/inter-company accounting if ever required.
   - Exact tax registration structure if multiple GST registrations exist.
   - Performance partitioning thresholds based on actual volume.

 APIF STATUS: FROZEN LOGICAL CONTRACT


 E1. API Architecture
 1. One versioned HTTPS JSON API serves web and Android clients.

 2. Business calculations, permissions and workflow transitions are server-authoritative.

 3. API version prefix is explicit, e.g. /api/v1/.

 4. Authentication/session/token implementation may follow chosen stack, but every private request is authenticated.

 5. Authorization checks role + action + data scope + approval limit on every protected endpoint.

 6. Write requests that can create money/stock/booking effects support idempotency keys.

 7. Concurrent edit protection uses record version/updated timestamp or equivalent optimistic concurrency control.

 8. List endpoints support pagination, filtering, sorting and server-side search.

 9. Errors use stable machine-readable error codes plus human-readable messages.

 10. File uploads are separate controlled multipart/upload flow with type/size validation.


 E2. Standard API Response Envelope
 { "data": ..., "meta": { ... }, "errors": [] }

   - Successful single-resource responses return data object.
   - List responses return data array plus pagination meta.
   - Validation/business errors return field/source references where possible.
   - Server never exposes stack traces or secrets to client.

 E3. HTTP / Error Semantics
  Status                 Frozen Meaning

  200                    Successful read/update/action.

  201                    Resource created.

  202                    Accepted async operation where used.

  400                    Malformed request / invalid syntax.

  403                    Authenticated but not authorized.

  404                    Resource not found or not visible in scope.

  409                    Conflict: duplicate, stale version, double booking, invalid state transition.

  422                    Business/field validation failed.

  429                    Rate limit.

  500                    Unexpected server error with trace/reference ID only.

 E6. Idempotency & Concurrency
   - Idempotency key mandatory for payment, receipt, stock movement, GRN posting, invoice finalization, event close/reopen
     and other configured critical writes.

   - Reusing the same idempotency key with a different payload is rejected.
   - Stale record version on update returns conflict; client reloads current record before retry.
   - Resource reservation/confirmation executes atomically to prevent double booking of stock/equipment/vehicle/capacity.
   - API retries must never duplicate journal lines, receipts, stock movements or external payment effects.

   - Every API error logs server trace/reference without exposing secrets to user.

 H1. Authentication & Authorization
   - Every private API requires authenticated session/token.

   - Server authorization is mandatory on read, write, approve, pay, reopen, export and admin actions.
   - Session expiry/revocation is enforced server-side.
   - Password/API/signing secrets are never stored in source code or client logs.

 H2. Data & Application Security
   - HTTPS only in production.
   - Input/schema validation on every write.
   - Parameterized ORM/query practices; no string-built SQL from user input.
   - Upload validation by type, size and content where feasible.
   - Sensitive logs are redacted.
   - Private customer/finance responses are not indexed/cached publicly.
   - Critical exports are permissioned, watermarked/logged if configured and audited.
   - Audit log records sensitive view/change/export/payment/approval actions according to policy.

 H3. Mobile Offline Freeze
 1. Offline read cache is encrypted/protected according to platform capability and contains only role-scoped data.

 2. Only explicitly allowed actions can be queued offline.

 3. Queued actions carry client-generated request ID/idempotency key.

 4. User can see Pending Sync, Synced, Conflict and Failed states.

 5. Conflict does not silently overwrite newer server data.

 6. Financial close, sensitive approval and configured high-risk actions may require online connection.

 7. Logout/session revocation clears or invalidates protected local data according to security policy.


 H4. Backup & Recovery Freeze
