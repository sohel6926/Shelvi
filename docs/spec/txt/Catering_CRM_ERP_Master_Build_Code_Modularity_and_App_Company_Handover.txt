2. Complete Project Functional Plan
2.1 Core Organisation & Master Data
• Company / Legal Entity -> Brand -> Branch -> Kitchen -> Store / Warehouse hierarchy.
• Customer, Venue, Item, Category, UOM & Conversion, Product/Dish, Recipe/BOM, Menu, Vendor, Outsource, Staff,
   Vehicle, Equipment/Asset, Booking, Event, Meal Session, Expense, Finance/Ledger and Role/Approval masters.
• One real item = one Item ID. Aliases and alternate spellings must not create duplicate master records.
• Item and Product/Dish remain separate. Recipe/BOM connects Products to Items.
• Standard Cost, Estimated Cost and Actual Cost remain separate.

2.2 CRM, Sales & Event Flow
• Lead -> Contacted -> Requirement Captured -> Quotation -> Negotiation -> Advance Pending -> Confirmed -> Event
   Planning -> Event Completed -> Payment Pending -> Closed.
• Customer -> Booking -> Event -> Sub-Event where applicable -> Meal Session.
• Quotation/version history, customer requirements, event/venue/session linkage and controlled status transitions.
• Event close includes operational close, returns, staff/vendor cost completion, customer/finance checks, provisional P&L
   and final financial close.

2.3 Food, Menu, Recipe & Production
• Menu -> Product/Dish -> Recipe/BOM -> Item/Ingredient.
• Recipes are versioned; approved versions are traceable to production and costing.
• Production, preparation, packing, dispatch and actual consumption must link back to Event/Meal Session where
  applicable.
• Actual consumption and stock are transaction-derived; no free manual stock balance edits.

2.4 Purchase, Inventory & Outsource
• Demand -> Purchase Requirement -> PR -> Vendor Quote/Comparison -> PO -> Delivery -> GRN -> QC -> Vendor Bill
   -> Payment.
• Stock changes only through Stock Movements.
• Inventory supports on-hand, committed/reserved, available, incoming, low-stock, expiry/wastage and location-based
   stock.
• Universal outsourced food/service engine for Pulka, Chapathi, Rumali Roti, Bobbatlu, Ice Cream, Pan/Paan and other
   outside services; do not build separate CRMs/databases for each.
• Purchase categories include Kirana, Vegetables, Disposables, Fruits, Non-Veg, Gas/Fuel, Water/Ice, Outside Purchases
   and Other Items.

2.5 Staff, Logistics, Expense & Finance
• Staff assignments, temporary staff, advances, cleaning, transport, vehicles, equipment and live-counter costs.
                          Catering CRM + ERP | Master Build + Code Modularity + App Company Handover
• Event-linked direct costs must flow to Event Actual Cost/P&L; Rent, Current Bill, WiFi and other general overheads
  remain overhead unless an approved allocation rule exists.
• Finance/Ledger remains authoritative for payments, collections, outstanding and settlement status.
• Advance is not automatically revenue; payment is not automatically expense.
• Revenue - Direct Cost = Contribution; Contribution - Allocated Overhead = Net Profit, using the frozen financial rules.

3.1 Calendar Clarity Rule
• Month-view date cell shows only 3-4 short chips; additional items show '+N more'.
• Clicking a date opens a grouped Day Details drawer for Festival, Events, Sessions, Work, Deliveries, Reminders,
  Payments and Vehicle/Equipment.
• Festival dates must not hide operational Events on the same date.
• Calendar is a visual/scheduling layer over source records, not a duplicate transaction database.

3.2 Purchase Search & Maintainability
• Every purchase category gets sticky live search, partial-word search, alias search, category/subcategory filtering and
  vertical scrolling.
• Universal Purchase Search queries all authoritative Item Master records without creating duplicates.
• Add Item is controlled by permission and duplicate detection.
• Never aggregate incompatible quantity units such as KG + Litre + Piece into one quantity total.

                       before final handover.

4.1 Change Isolation Rule
• A small change should normally touch only the relevant feature/page/component/service and its tests/docs.
• Do not regenerate a large working screen to add one field, one button or one validation rule.
• Before creating new code, search for reusable components, services, types, functions, tables and APIs.
• Refactor when responsibilities become mixed or navigation becomes risky - not only at final handover.
• After every meaningful change, update the Feature-to-Code Map so the next developer knows where the change
  belongs.

6. Code Language / Receiving Company Stack Rule
Important                 Source-code handover means delivering the complete editable source in the
                          language/framework the project actually uses. The receiving company's preferred language is a
                          migration decision, not a reason to hide, convert or rewrite the existing source without control.

• Document the actual current stack for Web, Mobile, Admin, Backend/API, Database, Auth, Realtime, Storage,
   Notifications and Hosting.
• Lock exact important versions and package/dependency files.
• If the receiving company uses a different language/framework, create a Stack Compatibility / Migration Matrix.
• For every mismatch record: current stack, target stack, compatible YES/NO, migration required YES/NO, affected
   modules/files and recommended continuation approach.
• Prefer incremental module-by-module migration when needed; do not blindly rewrite the entire application.
• The receiving company must receive enough source, documentation and test evidence to either continue in the current
   stack or plan a controlled migration.

8. Functional and Handover Acceptance
• A page/button is not completion. Save must persist, refresh must retain, correct permission must apply, backend
   transaction must be correct, calculations/reports must update and audit must be written where applicable.
• Double-click/idempotency protection must prevent duplicate critical transactions such as GRN, payment and stock
   movement.
• Cancellation/reversal must preserve history and reverse effects safely instead of deleting posted business history.
• Dashboard and report totals must reconcile to source transactions.
• Fresh-machine / replacement-developer test: clone -> configure -> run -> test core workflows -> build production.
• If hidden setup knowledge or the old developer's explanation is required, handover is NOT ready.
